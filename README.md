# Prices API

Сервис, который по расписанию забирает среднюю цену торговой пары (BNBUSDT) у биржи Binance, сохраняет её в БД и отдаёт через REST. 

## Архитектура

- **Controller:** принимает запрос, валидирует входные данные, отдаёт DTO.
    
- **Service:** бизнес-логика, транзакции, маппинг Entity в DTO через `MapStruct` (пакет `mapper`).
    
- **Repository:** - JPA Repository (`PriceRepository`) - базовые CRUD + кастомные native и JPQL запросы для достижения желаемой логики.

- **Entity:** `Price` с необходимыми для работы приложения полями.
    
- **DTO:** 

	- `AveragePriceReadDto` (для `/average`), `PriceReadDto` (для `/last-saved`), `PagingPricesResponse` (для пагинации), `TrendResponse` (для `/trend`).
	- `ErrorResponse` для формирования ответа об ошибках в `@RestControllerAdvice`.
    
- **Liquibase:** `db/changelog/changelog-1.yaml` для управления схемой БД, ввиду отсутствия необходимости в сложных миграциях, подключает `changelog-1.sql` файл с созданием таблицы.

## Быстрый запуск

```bash
# 1. Склонировать репозиторий
git clone https://github.com/Egrius/currency-service

# 2. Перейти в папку проекта (если не было git clone <url> .)
cd currency-service

# 3. Скопировать .env.example в .env и, если необходимо, задать свои параметры уже там (для демонстрации можно просто скопировать)

cp .env.example .env

# 4. Запустить командой
docker compose --env-file=./.env up --build
````

После запуска:

- API: http://localhost:8080/api/v1/prices
- Swagger UI: http://localhost:8080/swagger-ui.html
- OpenAPI JSON: http://localhost:8080/v3/api-docs

## Детали реализации

- ### Docker compose(`docker-compose.yaml`)
	Состоит из двух сервисов: БД и само приложение. В качестве БД используется `image` `postgres:16-alpine`, порты проброшены вручную. Используются `environment`-переменные, которые подтягиваются через `.env`-файл.

	Healthcheck не реализовывал, инструкции `depends_on` достаточно для успешного запуска и демонстрации работы.

- ### Поддерживаемые переменные окружения (`.env`)
	- `DB_HOST` - хост БД (в Docker-сети `db`, локально `localhost`)
	- `DB_PORT` - порт БД (по умолчанию `5432`)
	- `DB_NAME` - имя базы данных (`currency_db`)
	- `DB_USER` - имя пользователя БД (`postgres`)
	- `DB_PASSWORD` - пароль пользователя БД (`postgres`)
	- `BINANCE_POLL_INTERVAL` - интервал опроса в формате ISO-8601 (`PT30S`)
	- `BINANCE_INITIAL_DELAY` - начальная задержка перед первым запросом (`PT0S`)
	- `BINANCE_REQUESTED_SYMBOL` - символ торговой пары (`BNBUSDT`)

- ### Properties (`application.yaml`)
	Порт приложения `8080`, прописан вручную, environment переменную для порта не добавлял. 

	Параметры для работы с Binance находятся в `binance`:
	- `api` 
		- `url` - базовый URL Binance
		- `avg-price-url` - требуемый эндпоинт для получения цены
		  
	- `poll-interval` - частота вызова **scheduler**, можно переопределить. По дефолту стоит **PT30S** (30 секунд), чтобы соответствовать требованиям ТЗ. (Определяется переменной окружения `BINANCE_POLL_INTERVAL`)

	- `initial-delay` - начальная задержка **scheduler**'а, это свойство нужно только для тестирования, для удобства вынесено в отдельную переменную, по дефолту 0. (Определяется переменной окружения `BINANCE_INITIAL_DELAY`)

	- `symbol` - символ запрашиваемой валюты, для удобства также вынесен в отдельную переменную, используется значение "BNBUSDT". (Определяется переменной окружения `BINANCE_REQUESTED_SYMBOL`)

	- `trend.threshold` - значение порога изменения цены в процентах, при котором можно считать, что изменение достаточно для того, чтобы реагировать на тренд. Стоит `0.01`, переменной окружения не задаётся.

- ### Эндпоинты
	Реализовано 4 эндпоинта:
	
	- `GET /api/v1/prices/last-saved` -  (в ТЗ не был явно указан путь для первого эндпоинта, поэтому выделил его в `/last-saved`, чтобы не конфликтовать с эндпоинтом пагинации `/api/v1/prices`). В качестве ответа отдаёт информацию о последней сохраненной записи (наиболее актуальная информация).

	```bash
	curl -X GET "http://localhost:8080/api/v1/prices/last-saved"
	```

	- `GET /api/v1/prices/average` - выдаёт рассчитанную на основании имеющихся в сервисе данных информацию о средней цене торговой пары за определенный промежуток времени \[from, to] включительно.

	```bash
	curl -X GET "http://localhost:8080/api/v1/prices/average?from=2026-01-01T00:00:00Z&to=2026-12-30T00:00:00Z"
	```
	
	- `GET /api/v1/prices?from=...&to=...&page=0&size=20` - выдаёт записи, сохраненные в интервале \[from, to] включительно, с пагинацией.

	```bash
	 curl -X GET "http://localhost:8080/api/v1/prices?from=2026-01-01T00:00:00Z&to=2026-12-30T00:00:00Z&page=0&size=20"
	```

	- `GET /api/v1/prices/trend` - производит вычисление тренда по значениям в таблице в интервале \[from, to] включительно. Логика определения тренда будет описана ниже.

	```bash
	curl -X GET "http://localhost:8080/api/v1/prices/trend?from=2026-01-01T00:00:00Z&to=2026-12-30T00:00:00Z"
	```
	
	Для удобства тестирования добавил Swagger.

## Нюансы реализации

- ### Работа с Binance API и Rate Limits (`BinanceScheduler`)
	- Запросы выполняются через `RestClient` с таймаутами на подключение и чтение по 5 секунд, чтобы зависание внешнего API не блокировало поток шедулера.
	  
	- Согласно документации Binance, при превышении лимитов возвращается код `429 Too Many Requests` (или `418`, если продолжать слать запросы и получить временный бан IP) вместе с заголовком `Retry-After` в секундах.
	  
	- При получении `429`/`418` выбрасывается кастомное исключение `BinanceRateLimitException`, парсится `Retry-After` (если заголовка нет — берётся дефолт 60 секунд) и выставляется время `backOffUntil`. Пока текущее время меньше `backOffUntil`, следующие тики шедулера пропускают запросы к бирже.
	  
	- Все остальные ошибки (`5xx`, сетевые сбои, пустой ответ) перехватываются и логируются, благодаря чему расписание не останавливается.

	- Сам `BinanceScheduler` однопоточный - `spring.task.scheduling.pool.size: 1`

- ### Защита от дублей и хранение цен
	- Для работы с ценами везде используется `BigDecimal`, в БД колонка имеет тип `NUMERIC(20, 8)`.
	
	- На уровне таблицы `prices` добавлен constraint `UNIQUE(symbol, fetched_at)`, исключающий появление дублирующихся записей для одной пары в один и тот же момент времени. В самом `BinanceScheduler` я не ловил отдельно ``DataIntegrityViolationException`` на подобные случаи.

- ### Алгоритм расчёта тренда (`WIDTH_BUCKET`)
	Вместо того чтобы выгружать все записи за период в память приложения и считать тренд в Java, нашел более интересный способ через использование SQL-функции `WIDTH_BUCKET()`, благодаря чему получаю информацию по группам, а само количество групп определяю динамически в зависимости от длины запрошенного интервала: 
	
1. Временной интервал `[from, to]` делится на корзины (buckets). Количество корзин выбирается динамически в зависимости от длительности периода и `poll-interval` (от 2 до 25 корзин). 
	
	Причем, помимо заготовленных значений бакетов под определённые интервалы (к примеру для часа - 5, для дня - 10 и т.д.), вводится ещё и рассчитанное количество на основе длины самого интервала и интервала работы `BinanceScheduler`.
	
	В итоге количество бакетов выбирается следующим образом: `int bucketsCount = (int) Math.max(MIN_BUCKETS_COUNT, Math.min(calculatedBucketCount, rangedBucketCount));` 
	(`MIN_BUCKETS_COUNT` - дефолтный минимум, равен 2, `calculatedBucketCount` - высчитанное количество, `rangedBucketCount` - заготовленные значения)
		
	Это нужно для того, чтобы не разбивать огромный диапазон на огромное количество бакетов и в то же время не разбивать маленький диапазон на слишком маленькое количество бакетов. Учитывается также и частота запроса шедуллером. Например, если мой интервал равен `1 минуте`, то заготовленное значение в 5 бакетов для диапазонов *меньших одного часа* является слишком большим числом, но может быть такая ситуация, что частота `BinanceScheduler` слишком высокая и условно за `1 минуту` в БД очень много записей, поэтому разбить диапазон на 5 уже вполне себе хорошая идея, таким образом не сильно размывать средние значения в бакетах.

2. Чтобы запись, попавшая ровно на верхнюю границу `to`, не улетала в дополнительную корзину `bucketsCount + 1` (особенность работы `WIDTH_BUCKET`, где верхняя граница не включительна), вызов обёрнут в `LEAST(WIDTH_BUCKET(...), :bucketsCount)`, чтобы ограничиться заданным количеством бакетов.
	   (Первым способом исправить такое поведение была попытка добавлять 0.001 секунду к дате, но это приводило к неправильному поведению - даты неправильно распределялись между бакетами и высчитанная средняя цена не соответствовала ожидаемой).

3. В каждой непустой корзине БД считает среднюю цену (`AVG(price)`). Далее сервис берёт среднюю цену первой непустой корзины и последней непустой корзины, считает процент изменения и сравнивает его с порогом `binance.trend.threshold` (`0.01%`):
	
 - Если изменение меньше порога (или данных нет / всего одна запись) — возвращается `FLAT`.
 - Если изменение `>= threshold` — возвращается `UPWARD` или `DOWNWARD` в зависимости от знака разницы.
		
4. **Краевой случай:** если пользователь запросил большой диапазон, но все реальные записи в БД лежат кучно в начале периода и попали в одну единственную корзину, сервис берёт фактические границы этих записей `[minFetchedAt, maxFetchedAt]` и делает повторное разбиение уже этого узкого участка на 2 подкорзины, чтобы корректно определить локальный тренд. Т.е. для каждой группы в SQL дополнительно извлекаются `MIN(fetched_at) as minFetchedAt` и `MAX(fetched_at) as maxFetchedAt`.
